# DKLA (Danny Kind Legal Atlas): instructions for coding agents

`DKLA-r19.html` is the current atlas (see Revisions 18 and 19); `DKLA-r8.html` is the working copy that revisions 9–15 rebuilt. It is a single-page app whose data, styles and code all live inline in the HTML, except for source-page images and PDFs, which live in `DKLA-sources/` and are referenced by relative paths such as `"DKLA-sources/contracts-casebook/printed-page-0001.webp"`. The HTML and the `DKLA-sources/` folder must stay side by side, because the browser loads each page image from that folder when the reader opens it.

## Reading the file safely

The HTML is about 17 MB, and several `<script type="application/json">` blocks are single lines several megabytes long. Never print the whole file or a whole JSON block. Locate blocks by id and read bounded slices, or parse a block with a short Python or Node script and print only the fields you need.

| Block id | Kind | Approx. size | Contents |
|---|---|---|---|
| `seedData` | JSON | 6.3 MB | The atlas graph: nodes (cases, doctrines, notes), edges, courses, map positions. This is the main editable data. |
| `textbookUpdate` | JSON | 0.8 MB | Patch applied by the "textbook" import mode. |
| `bookArchive` | JSON | 2.4 MB | Contracts casebook pages keyed by printed page: text, assignments, linked node ids, `image` path. |
| `suppArchive` | JSON | 0.4 MB | Contracts supplement pages, same shape as `bookArchive`. |
| `civilArchive` | JSON | 4.1 MB | Civil Procedure page text and PDF-page mapping; `casebookPDF`, `malloryPDF`, `syllabusPDF` are paths to PDFs; `malloryImages`, `syllabusImages` are paths to images. |
| `lrsArchive` | JSON | 2.7 MB | Legislation and the Regulatory State sources: page text, printed labels, checksums, `image` paths. |
| `lrsSyllabusText`, `dklaIcons` | JSON | small | LRS syllabus text; icon definitions. |
| `appCode`, `compatCode`, `studyCode`, `semesterCode`, `civilCode`, `dklaCore`, `dklaUI` | JS | 6–63 KB each | Application code, loaded in that order; later layers override earlier functions. |

Style blocks load in the same order (`studyStyle`, `semesterStyle`, `civilStyle`, `dklaStyles`, `dklaR9Styles`); the last one holds the revision-9 presentation overrides.

## Revision 14 (27 September 2026)

The map text was rewritten after the owner rejected the overlapping, tiny and washed-out text of revisions 11–13. What had been wrong: screen-space fonts were placed in world-space boxes with no rule for what happens when they do not fit; several kinds of text (district questions, rows, the "related notes" line, cards) were drawn outside the label collision engine; secondary text was 10.5 px with a 2.4 px dark halo whatever the box size; the HTML overlays were never considered; and the work was only ever checked at one viewport. The rules now in force, all in `tools/r11/renderer.js` unless noted:

- **One label engine for everything.** Every piece of map text goes through `putLabel` and `resolveLabels` (priority sort, 48 px screen grid, 300 ms fades): course names, zone titles with their subtitles (one label), subject titles, route questions, tallies, descriptions, principal cases, the subtopic list, subtopic titles, district questions and case rows, the "related notes" line, ribbon-end pills, spine labels and annotations. Every drawn card registers a blocker label (`cb:` key, `nocollide`, priority .6), so nothing is ever written over a card. The HTML overlays (`.map-nav`, `#mapWelcome`, `#mapHint`, `#saveStatus`, `#inspector`, `.zoom-controls`) are measured every frame (`frameChrome`) and claimed first, so map text passing under them hides instead of showing through. Priorities: cards .6, zone titles .8, subject titles 1–1.5, pills 1.5, subtopic titles 2, district questions 2.4, rows 2.6, route questions 3, tallies 3, descriptions 3.5, principal cases 4, subtopic list 4.3+. `R11.blockedBy` records which label blocked which (read by `tools/r14/qa/flick.js` and `probe.js`); `fast` labels (district questions and rows) vanish at once when cards replace them.
- **Fit or hide.** A subject title is drawn only at 10.5 px or more and only if it fits its box (two lines; at the floor, tiles under 120 px show a name only when the whole name fits, otherwise the hover tip names them, and the step badge appears only from 120 px and only while the title is visible). The title is capped by the headroom above the first subtopic. Secondary text scales with the box (`sfs`, 10.5–14 px by box width, never under 10.5 px, line height 1.45) in a lightened tint of the subject colour, with no halo inside a box; halos elsewhere scale with the font (1.1–2.4 px). Cards never start under 12 px.
- **Three subject modes.** `star` (a coloured tile), `mid` (a summary: route question, tally, description unless boilerplate, principal cases, then the subtopic list as a table of contents, each row clickable, with "… and N more" when cut) and `full` (subtopics and cards), decided by headroom in pixels (`fullOn` at 52 px). The summary admits its lines in a fixed order and only adds lines as the zoom grows, so nothing appears and then vanishes. A subject never shows its summary and its cards together; selected or connected cards are forced only when they are at least 110×26 px.
- **Connections.** Ribbons curve toward their target (no loops). A ribbon into a subject that is not showing its cards ends at the subject's edge, and the far ends in one subject share a single pill outside the tile ("A · B +3", click opens the subject); pills inside a subject are placed at the entry's own card only when the subject is in `full` mode.
- **Colour.** Tiles are solid at the floor and the course fit (fill .8, stroke .95) and fade only as subtopics appear; Civil Procedure subjects carry twelve distinct hues (`CP_HUES` in `tools/r12_layout.py`); ribbons are drawn at .74 opacity. Zone outlines, spine links and annotations are drawn only when a course is open (annotations only the `large` ones); the zone outline appears only when its title fits.
- **Layout (`tools/r12_layout.py`).** Boxes shrink to their contents: a subtopic ends 36 units under its last card, a subject 48 units under its last subtopic (never under 1,000 tall), a zone 70 units under its last subject (360 units of headroom above its first row); `courseBlocks` are recomputed afterwards. The study workbench and the legal dictionary sit at the centre of the triangle, in the gap between Civil Procedure and LRS (`GAP` 4000 across, `GAP_Y` 3600 down).
- **Camera (`tools/r11_apply_renderer.py`, `R11.step`/`R11.wheel`/`levelTargets` in the renderer; revision 14c).** Zoom is stepped: the camera stops only at four levels, atlas (`home('Atlas')`), course (`home(course)`), subject (`goRegion`, fit at up to .95) and subtopic (`goDistrict`, fit at up to 1.05), so every view is one the renderer is designed for. A wheel notch, a trackpad flick (the wheel must fall silent for 250 ms before the next step; inertial scrolling keeps the lock), a pinch past 1.3× or the +/- buttons move one level toward what is under the pointer (the containing course, subject or subtopic, else the nearest one); zooming out goes to the containing level; clicking a subject or subtopic goes straight to its level; panning is free at every level; Alt + wheel still zooms continuously (cap 1.25). The current level is inferred from the zoom nearest in log space to the four fits for the point under the pointer, so it survives panning and the reading panel's narrower safe area. The welcome block is excluded from the safe area at every width. The hover tip names only tiles under 200 px wide and closes once a tile is wider.
- **Dictionary (revision 14b, same day).** The owner uploaded `added-sources/Cornell_Wex_Dictionary_2026-09-26.pdf`, the full text of the Wex catalogue. `tools/r14/wex_extract.py` pulls page text and link annotations into `wex_pages.json` (scratch), `tools/r14/wex_dictionary.py` parses the 5,654 articles and writes `added-sources/glossary/glossary.json` as **Wex only** (5,565 terms; Black's, Bouvier, the court glossaries and the editorial entries are gone) plus `wex-cases.json`, the Wex articles about cases the atlas teaches (matched by party names). `tools/r14_wex_cases.py`, new in the rebuild chain after `r12_fix_sources.py`, attaches those to the case entries as a source chip and a notes paragraph; Wex articles about cases outside the courses stay in the dictionary only when substantive (`kind: "case"`, shown with a "landmark case" tag). Rebuild order: as revision 13, with `r14_briefs.py` then `r14_wex_cases.py` before `r12_glossary.py`; `tools/rebuild.sh` runs the whole chain from any checkout (`DKLA_BASE` = the revision-10 file).
- **Checks (`tools/r14/qa/`, see its README).** `audit.js` counts overlapping, overflowing and sub-9.5 px text at five viewports (target 0/0/0); `audit2.js` adds every wheel tick and selected-entry states with ribbons; `continuity.js` and `flick.js` catch labels that appear, vanish and reappear (labels passing under the HTML overlays are reported as "blocked by chrome" and are expected); `probe.js` dumps one state; `look.js` takes the screenshots to look at. ## Rules

- Do not convert source paths back into base64 or `data:` URIs inside `DKLA-r8.html`; that would recreate the 363 MB file.
- To add a new source page, save the image or PDF under `DKLA-sources/` and put its relative path where the code expects an image or PDF value. Add an entry for the new file to `DKLA-sources/manifest.json` (path, archive, mime, encoding `datauri` for images or `base64` for PDFs, bytes, sha256) if it should be included in standalone builds.
- The browser opens this file from `file://`, so JavaScript cannot `fetch()` files from `DKLA-sources/`. Load sources through `<img src>`, `<iframe src>` or `<a href>` only.
- `python3 tools/build_standalone.py` builds `DKLA-standalone.html`, a single self-contained file with every source inlined. Built from the unedited `DKLA-r8.html`, it is byte-identical to the original `DKLA-r8-rebuilt.html`; run it after edits to confirm that every source path still resolves (it warns about missing paths or changed files).

## r20.9 (2026-10-10): doctrine timelines audited and rebuilt

The owner asked for every case whose doctrine developed over time to sit in a timeline, and for every timeline to be in the right order, show how the doctrine moved and carry the relevant information. The old set (`seedData.timelines`, r9b, 22 timelines, 164 steps) had steps out of order (Brand X before Mead; the 1986 summary-judgment trilogy), a consideration case leading the reliance line (Hamer), timelines that ran two or three doctrines together (personal jurisdiction, standing, due process hearings, rulemaking, damages) and 231 of the 392 cases in no timeline at all.

- **Data: `tools/r19/data/timelines.json`.** 66 timelines (21 Contracts, 24 Civil Procedure, 21 LRS), 505 steps; 376 of 392 cases are in at least one. Each timeline has `id`, `course`, `title`, `question`, `now` (where the doctrine stands, October 2026) and `steps`. A step is one of: `id` (a map Case or Rule entry), `sup` (a supporting case's brief id; it opens the brief), or `event` (a dated statute, rule amendment or Restatement with no entry; shown, not linked). Every step has `year`, `turn` (`origin`, `expands`, `narrows`, `refines`, `reaffirms`, `overrules`, `codifies`, `divided`, `counterpoint`, `applies`) and a one-sentence `note` on what moved; `date` (YYYY-MM-DD) is given wherever two steps share a year; `fate` records a later overruling, abrogation or supersession. `left_out` lists the 16 map cases in no timeline, each with the reason. A case sits in at most two timelines, and only when it belongs to both.
- **How it was made.** Three course editors (one agent each) re-cut the timelines from the map cases, the supporting briefs and the Rule entries, checking each note against the atlas brief and web sources; three separate fact-checkers who had not written them checked every year, date, note, turn, fate and `now` line (16 corrections, applied); the lead editor reviewed all of it and added Lucy v. Zehmer and Lefkowitz to the acceptance line, Noel Canning to appointments, Collins v. Yellen to removal and Restatement § 45 to firm offers. Decisions from 2025-2026 are described as the atlas briefs describe them. Pennoyer is dated January 21, 1878 (October Term 1877); its entry title still says 1877.
- **Build.** `load_timelines` in `tools/r19/assemble.py` refuses the file if a step's id is not a map Case or Rule, a `sup` is not a supporting case, steps are out of date order, a timeline has fewer than three steps, or a turn is not in the list; the set goes into `dklaR19Data.timelines` with a `rev` stamp derived from its content.
- **Runtime: `tools/r19/timelines.js` and `timelines.css`** (appended after r20.js / r20.css). Nothing in `seedData` changes. Once the atlas is ready (and before every panel render) the saved graph's `timelines` is replaced by the new set unless `data.timelinesRev` already equals the stamp, so the browser cache takes a new set whenever the file changes. Steps that are not map entries get ids that match no entry (`sup:<id>`, `event:<timeline>:<n>`), so the r9b panel code that walks the steps skips them. After dklaUI draws a timeline in the reading panel (matched by its title), it is redrawn from the full data: turn tag, note, fate line, supporting-case and event steps (outlined year pills), a "Where it stands" box and an "All doctrine timelines" link. A concept that is not itself a step shows the two timelines that use it most and names the rest in an "Also traced in" line. `#r21Timelines` lists every timeline by course (cards, then a vertical view of one timeline); it opens from the More menu ("Doctrine timelines"), the panel link and search rows (every word of the query must appear in the title, question, `now` line or step names). Public handle: `window.DKLATimelines` (`open(id)`, `list()`, `rev`).
- **To change a timeline,** edit `timelines.json` and rebuild r20; the new `rev` makes every browser take the change. Do not edit `seedData.timelines`: it is only the fallback before the layer runs.
